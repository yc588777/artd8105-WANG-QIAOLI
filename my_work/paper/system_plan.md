## 0 · 设计原则

1. **研究先于功能。** 每个功能都必须产生一种可分析的数据，或者支撑一种可观察的确认行为；做不到的功能不做。
2. **不打断共创。** 记录在后台自动完成，参与者不需要额外操作。界面只多出一条方案栏和一个标注工具。
3. **两类判断分开。** 机器的判断（能否打印）与手艺人的判断（能否编、好不好）在数据结构和界面上都分开存储、分开显示，永远不合并成一个“通过”。
4. **版本冻结。** 每轮共创开始前冻结系统版本，轮次之间的改动全部记入设计修订日志（D9）。这样论文可以说清楚每轮用的是哪个系统。
5. **可离线、可携带。** 会话数据存放在本机文件里，可以打包带到手艺人的电脑上，复用现有便携包。

## 2 · 功能规格

### F1 · 会话与方案快照（版本链）

**为什么：** 确认事件的单位是“某个版本的方案”。没有版本，就无法说清楚手艺人确认的是哪一个（RQ1、RQ2）。

**数据结构**（`data/sessions/{session_id}/session.json`）：

```json
{
  "id": "s-20261211-r1",
  "round": "R1",
  "title": "R1 读系统",
  "participants": [{"code": "C1", "role": "craftsperson"}, {"code": "D0", "role": "designer"}],
  "system_version": "git 短哈希或构建时间",
  "consent_logging": true,
  "created": "ISO 时间",
  "snapshots": [
    {
      "id": "snap-007",
      "parent": "snap-005",
      "author": "D0",
      "created": "ISO 时间",
      "label": "菱纹加弧 · 收边放宽",
      "params": { "...": "完整 WeaveParams" },
      "machine": {"exportable": true, "reasons": [], "counters": {"interior_endpoint_count": 0}},
      "status": "proposed",
      "plan_png": "snap-007_plan.png",
      "media": []
    }
  ]
}
```

**后端接口**（新增 `backend/app/sessions.py`，在 `main.py` 中挂载）：

- `POST /api/sessions` 新建会话（轮次、参与者编号、记录同意）。
- `GET /api/sessions`、`GET /api/sessions/{id}`。
- `POST /api/sessions/{id}/snapshots`：保存当前参数，后端跑一次 draft 级 `build_unified`，写入 `machine` 摘要与平面图。
- `GET /api/sessions/{id}/snapshots/{sid}`；`POST .../{sid}/restore` 把参数载入编辑器。
- `GET /api/sessions/{id}/bundle`：打包会话目录为 zip，供分析与带走。

**前端：** 顶部新增“方案栏”。

- 左侧：会话名与轮次，当前角色切换（手艺人 / 设计师 / 研究者）。
- 中间：快照时间轴，缩略图按确认状态着色，点击即恢复。
- 右侧：“存为方案”按钮。

**验收：** 连续存 20 个快照，任意恢复后参数与平面图完全一致；父子关系可以画成树。

### F2 · 标注

**为什么：** 手艺人的判断要落在模型的具体位置上（某个交点、某段收边），才能编码为“依据哪类知识、指向哪个表征”（RQ1）。

**交互：**

- 在平面图或三维视图上点击，落一个标注点。三维视图用射线求交，再换算为扇面毫米坐标。
- 点击位置在 3 mm 内若有交点，自动吸附到该交点并记录交点编号；靠近边框时标为“收边”。
- 弹出小卡片，选择**类别**和**判断**，可写一句话。

**类别：** 挑压 / 收边 / 疏密 / 篾性 / 造型 / 其他。这与论文编码表的“知识类型”对应，现场选的类别只作为初始编码，分析时由研究者复核。

**判断：** 可编 / 要改 / 编不出 / 说不准。

**数据**（`session.json` 内 `annotations` 数组）：`{id, snapshot, author, created, x_mm, y_mm, target: {kind: crossing|rim|region, ref}, category, verdict, text}`。

**后端：** 新增 `GET /api/weave/crossings`，从 `compose_layers` 返回全部交点 `{id, x, y, over, under}`，现有 `crossings_preview` 只有 8 个，不够用。另加 `POST/PATCH/DELETE /api/sessions/{id}/annotations`。

**验收：** 在三维视图和平面图上各落 10 个点，与同一交点的吸附误差小于 1 mm；切换快照时标注随快照显示或隐藏。

### F3 · 确认状态

**为什么：** RQ2 要追踪确认如何在屏幕、打印件与手之间移动，需要一个明确的状态链。

**状态机：**

```
proposed（设计师提出）
  → revised（手艺人要求修改，生成子快照）
  → craft_confirmed（手艺人确认可编） | craft_rejected（手艺人判定编不出，必须填理由）
  → printed（已打印，附照片）
  → woven（已真竹试编，附照片）
  → overturned（任何后续阶段推翻先前确认，必须填理由与推翻发生的阶段）
```

**规则：**

- 只有手艺人角色可以设置 `craft_confirmed` 和 `craft_rejected`。
- 每次状态变化都写入事件日志（F8），记录角色和时间。
- `overturned` 不覆盖旧状态，而是追加，保留完整路径。

**前端：** 快照卡片上显示状态徽标，点开可以看到这个方案的状态历史。

**验收：** 一个方案走完 proposed → craft_confirmed → printed → overturned 后，能完整导出它的路径。

### F4 · 两类拒绝与通俗解释

**为什么：** 设计含义二“让拒绝可解释”需要证据。界面必须让参与者分得清“机器说不行”和“手艺人说不行”（RQ1、RQ3）。

**机器拒绝：** 把 `master_lock.py` 的闸门计数翻译成通俗语言，并附修正方向：

| 计数 | 通俗说法（繁中界面另译） | 修正方向 |
|---|---|---|
| `interior_endpoint_count`、`visible_endpoint_count` | 有篾条在扇面中间断了头 | 减小密度，或换整条走向 |
| `short_fragment_count` | 有过短的篾段，打印会掉 | 减小密度、加宽条带 |
| `insufficient_embed_count` | 有篾条没有扎进边框 | 收小弧度，或调整方向 |
| `unanchored_strip_count` | 有篾条悬空 | 同上 |
| `path_discontinuity_count` | 篾条中途跳断 | 降低规則度的随机 |
| `boundary_edge_count`、`non_manifold_edge_count` | 模型没有合成一整件 | 降低起伏或底编密度 |

- **一键修正：** 后端按修正方向依次尝试若干组小幅参数调整，用 draft 级预览找到第一组通过闸门的参数，作为建议展示；用户可以接受或拒绝。
- 接受与拒绝都写入日志，事件类型为 `fix_offer` 和 `fix_accept`/`fix_reject`。

**手艺人拒绝：** 来自 F2 中判断为“编不出”的标注和 F3 的 `craft_rejected`，在界面上单独用一种颜色和图标显示。

**验收：** 在 6 种计数各自被触发的参数下，都能显示对应的说法；一键修正在 10 秒内给出建议，或明确提示“找不到附近可行解”。

### F5 · 工艺图纸

**为什么：** 回答 RQ2 中“打印件之外，方案能否回到真竹”。手艺人对图纸的修改本身就是研究数据。

**后端：** 新增 `POST /api/weave/craft-sheet`，在 `compose_layers` 的条带与交点数据上计算：

- **每根篾条：** 编号、所属族（甲/乙/底编）、展开长度（含两端埋入）、两端入框位置、最小曲率半径。
- **挑压序列：** 沿篾条顺序列出每个交点的上或下，并压缩成工艺写法，例如“压二挑一 ×6”。
- **汇总：** 篾条总数、按族统计的根数与长度、建议备料长度（展开长度加上手艺人设定的余量）。
- **可行性标注：** 最小曲率半径小于阈值 \(R_{min}\) 的篾条标为“仅打印”。\(R_{min}\) 在 R1 中由手艺人提供或校准，系统默认值只作为占位。阈值从哪里来，本身就是论文第 6.3 节的一条发现。

**输出：**

- 一个 SVG：扇面平面图，篾条编号，起编点标记。
- 一个可打印的 HTML 页面：表格，加上浏览器“打印为 PDF”。不新增 PDF 依赖。

**验收：** 对参考预设生成图纸，篾条数与 `curve_count` 一致；手工抽查 3 根篾条的挑压序列与三维视图一致。

### F6 · 挑压视图

**为什么：** 手艺人读的是挑压，不是曲面。RQ1 需要观察这一表征被怎样使用。

- **着色模式：** 在 `Viewer.tsx` 中按交点上下着色：压在上的一段用暖色，被压的用冷色。
- **剖面：** 点击一根篾条，沿它显示高度曲线，标出交点与边框余量（数据来自 `master_lock._ribbon_record` 的逐点高度）。
- **交点编号：** 可开关显示，与 F2 的吸附和 F5 的序列使用同一套编号。

**验收：** 剖面上交点的位置与 F5 序列一致；开关切换不需要重新计算模型。

### F7 · 三方并排

**为什么：** RQ2 的分析需要把屏幕方案、打印件、真竹片放在一起；R3 的讨论也在这个视图里进行。

- **媒体上传：** `POST /api/sessions/{id}/snapshots/{sid}/media`，类型为 `print_photo` 或 `bamboo_photo`，附拍摄说明。
- **并排视图：** 平面图 + 三维截图 | 打印件照片 | 真竹片照片，标注可以叠加在平面图上。

**验收：** 一个方案可以挂 6 张以上照片；并排视图可以直接导出为 PNG，作为论文图的素材。

### F8 · 研究记录

**为什么：** 论文第 6 节的确认事件时间线、表征使用统计都要从这里来（D2）。

- **存储：** 每个会话一个只追加的 `events.jsonl`。只有 `consent_logging` 为 true 时才写入；界面右上角显示“记录中”。
- **事件类型：**
  - `param_change`：停手 800 ms 后合并为一条，记录键、旧值、新值；
  - `preset_load`
  - `snapshot_create`、`snapshot_restore`
  - `annotation_add`、`annotation_edit`
  - `status_change`
  - `gate_block`、`fix_offer`、`fix_accept`、`fix_reject`
  - `view_toggle`：挑压视图、剖面、平面或三维；
  - `craft_sheet_open`
  - `export`
- **字段：** `t`（ISO 时间）、`session_clock`（会话开始起的秒数）、`role`、`participant`、`type`、`payload`。
- **与录像对齐：** 界面角落持续显示会话时钟。录像开始时对着屏幕拍一下，就能用它对齐。
- **隐私：** 不记录姓名，只用参与者编号；不联网，数据只在本机。

**验收：** 一次 30 分钟模拟会话的事件能完整导出；用 `session_clock` 对齐录像的误差小于 2 秒。

### F9 · 版本冻结与设计修订日志

**为什么：** RtD 研究必须说清楚系统在研究过程中怎样改变（RQ3、D9）。

- 每个会话记录 `system_version`。界面“說明”页显示当前版本号。
- 在 `my_work/process_journal/design_revisions.md` 中，每次轮次间的修改记一条：日期、触发它的观察（引用会话和事件编号）、改了什么、预期影响。
- 轮次进行中不改系统，突发故障除外，修复需要记录。

## 5 · 风险与备选

| 风险 | 备选 |
|---|---|
| 三维视图标注的射线求交不稳 | 只在平面图上标注，平面坐标与三维一一对应 |
| 一键修正太慢 | 改为只显示修正方向，不自动求解 |
| \(R_{min}\) 手艺人说不出一个数 | 让手艺人用真篾条弯给你看，测量弯折处的半径，作为 D7 数据记录 |
| 手艺人的电脑不能运行 | 用便携包；再不行，就带自己的笔记本到现场 |
| 记录同意被撤回 | 停止记录，已有数据按约定删除；论文只用剩余的同意数据 |
